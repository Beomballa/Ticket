# 재고 잠금 전략 비교 실험

- 측정일: 2026-09-11
- 목적: 단일 인기 재고의 고경합 차감 방식 선택

## 실험 조건

| 항목 | 값 |
|---|---:|
| Java | 21.0.10 |
| 데이터베이스 | PostgreSQL 16-alpine, Testcontainers |
| 초기 재고 | 100 |
| 요청 | 전략별 1,000건, 요청당 1개 차감 |
| 동시 실행 | 고정 스레드 32개 |
| DB 연결 | HikariCP 기본 최대 10개 |
| 트랜잭션 | 요청당 1개 |
| 낙관적 락 재시도 | 없음 |

각 전략은 별도 재고 행에서 실행했다. TPS는 재고 소진 응답을 포함한 전체 1,000건의 완료
처리량이며, p95도 성공·충돌·재고 소진 응답 전체의 요청 지연이다. 충돌은 낙관적 버전 조건이
맞지 않아 UPDATE가 실패한 경우이고 재고 소진과 별도로 집계했다.

## 전략

1. 낙관적 락: 수량과 version을 조회한 뒤 `WHERE version = ?` 조건으로 차감한다.
2. 비관적 락: `SELECT ... FOR UPDATE`로 행을 잠근 뒤 수량을 확인하고 차감한다.
3. 조건부 UPDATE: `available_quantity >= 1` 조건으로 검사와 차감을 한 문장에서 수행한다.

## 측정 결과

| 전략 | 성공 | 충돌 | 재고 소진 | 충돌률 | SQL 실행 | TPS | p95 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 낙관적 락 | 100 | 549 | 351 | 54.90% | 1,649 | 2,963.86 | 32.12ms |
| 비관적 락 | 100 | 0 | 900 | 0.00% | 1,100 | 2,476.35 | 39.05ms |
| 조건부 UPDATE | 100 | 0 | 900 | 0.00% | 1,000 | 7,105.08 | 15.97ms |

모든 전략에서 `성공 수 + 최종 재고 = 초기 재고`, 최종 재고 0, 음수 재고 없음이 성립했다.
SQL 실행 수는 트랜잭션 제어문을 제외한 재고 SELECT·UPDATE 횟수다. 낙관적 락은 모든 요청의
SELECT 1,000회와 재고가 남아 있던 성공·충돌 요청의 UPDATE 649회가 필요했다. 비관적 락은 잠금
SELECT 1,000회와 성공 UPDATE 100회, 조건부 UPDATE는 요청당 UPDATE 1회만 실행했다.

## 해석과 선택

낙관적 락은 DB 대기를 피하지만 이 부하에서는 절반 이상의 요청이 버전 충돌로 끝났다. 실제
서비스가 이를 재시도하면 DB 부하와 꼬리 지연이 추가된다. 비관적 락은 충돌 오류 없이 판매를
완료하지만 모든 요청을 행 잠금에서 직렬화해 p95가 가장 높았다.

조건부 UPDATE는 별도 읽기와 애플리케이션 재시도가 없고, 재고 부족도 영향 행 수로 판단할 수
있다. 이번 기준선에서 처리량과 p95가 모두 가장 좋아 운영 구현으로 선택했다.

## 재현

```bash
./gradlew test --tests '*comparesStockConcurrencyStrategiesWithoutOverselling' --info
```

`STOCK_CONCURRENCY_RESULT`로 시작하는 세 줄이 측정 결과다. 테스트는 각 전략의 요청 수,
성공 수, 최종 재고와 초과 판매 방지를 자동 검증한다.

## 한계와 후속 측정

- 로컬 단일 프로세스·단일 DB 컨테이너의 1회 결과이므로 운영 용량 수치가 아니다.
- 재고가 소진된 뒤의 900개 요청이 포함되어 판매 가능 구간만의 지연과는 다르다.
- HTTP, 인증, 멱등키와 예약 INSERT 비용을 제외한 재고 경합 마이크로 기준선이다.
- 운영 후보 환경에서는 반복 실행의 중앙값, 판매 가능 구간 p95, DB lock wait, CPU·I/O와
  커넥션 풀 대기를 추가 측정한다.
- 다중 재고 예약과 취소가 섞인 부하에서 ID 정렬이 교착을 충분히 억제하는지 별도로 검증한다.
