# ADR-0009: Transactional Outbox와 멱등 소비

- 상태: 승인
- 결정일: 2026-09-12

## 맥락

예약 확정·취소·만료 후 감사 로그나 알림 같은 후속 작업이 필요하다. DB 상태 변경 후 직접 외부
작업을 호출하면 DB 롤백과 외부 성공 사이에 불일치가 생긴다. 반대로 커밋 뒤 이벤트를 저장하면
프로세스 중단 시 이벤트가 유실된다. 폴링 퍼블리셔는 중복 전달될 수 있으므로 소비자도 멱등해야
한다.

## 결정

- 예약의 `CONFIRMED`, `CANCELLED`, `EXPIRED` 전이와 Outbox 이벤트 INSERT를 같은 DB
  트랜잭션에서 처리한다.
- 이벤트 payload에는 예약 ID, 상태, 총액과 발생 시각만 저장한다. 엔티티 전체나 민감정보는
  포함하지 않는다.
- 폴러는 `PENDING`, 재시도 가능한 `FAILED`, 임대가 만료된 `PROCESSING` 이벤트를
  `FOR UPDATE SKIP LOCKED`로 최대 20건 선점한다.
- 선점 트랜잭션에서 상태를 `PROCESSING`으로 바꾸고 시도 횟수와 30초 처리 임대를 저장한 뒤
  커밋한다. 실제 소비는 이 트랜잭션 밖에서 실행한다.
- 성공은 별도 트랜잭션에서 `PUBLISHED`로 기록한다. 소비 후 성공 기록 전에 중단되면 임대 만료
  뒤 재전달한다.
- 실패는 기본 1초, 최대 1분의 지수 백오프를 적용한다. 기본 최대 시도 횟수는 5회이며 이후
  `FAILED` 상태로 격리한다.
- 각 소비자는 `(consumer_name, event_id)` 처리 이력을 부작용과 같은 트랜잭션에서 먼저
  INSERT한다. 이미 존재하면 부작용을 건너뛴다.
- 첫 소비자는 예약 이벤트를 `audit_logs`에 기록한다.

## 보장 범위

- 예약 상태 변경과 Outbox 저장: 원자적이다.
- Outbox 전달: at-least-once다. 임대와 재시도로 유실을 줄이지만 중복 전달은 허용한다.
- 동일 PostgreSQL 트랜잭션에 참여하는 소비자 부작용: 처리 이력으로 한 번만 반영한다.
- 외부 이메일·PG·메시지 브로커: exactly-once를 보장하지 않는다. 외부 시스템의 멱등키 또는
  별도 전달 기록이 필요하다.

## 대안

- 예약 트랜잭션에서 후속 작업을 직접 호출하는 방식은 외부 지연이 DB 잠금 시간을 늘리고
  실패 원자성을 보장하지 못해 제외했다.
- 애플리케이션 이벤트의 커밋 후 리스너만 사용하는 방식은 프로세스 중단 시 이벤트 유실 구간이
  있어 제외했다.
- 메시지 브로커부터 도입하는 방식은 현재 규모에서 운영 요소를 늘리므로 Outbox 계약과 재처리
  기준을 먼저 고정한다.

## 결과와 남은 위험

강제 롤백 시 예약 이벤트가 남지 않으며, 소비자 실패 시 처리 이력과 감사 로그가 함께 롤백된다.
재시도 성공과 동일 이벤트 재전달에서도 감사 로그는 한 번만 저장된다. 처리 도중 프로세스가
중단되면 30초 뒤 다른 인스턴스가 회수할 수 있다.

최대 시도에 도달한 이벤트를 조회·재처리하는 관리자 경로와 적체·실패·처리 지연 메트릭은 운영
단계에서 추가한다. 이벤트 스키마 버전과 하위 호환성 정책도 실제 외부 소비자를 연결하기 전에
정의해야 한다.
