# ADR-0006: 예약 생성·확정 멱등키

- 상태: 승인
- 결정일: 2026-09-11

## 맥락

클라이언트의 타임아웃이나 네트워크 재시도는 같은 예약 생성 또는 결제 확정 요청을 여러 번
전달할 수 있다. 순차 중복뿐 아니라 동시에 도착한 요청에서도 예약, 재고 차감과 결제 승인은
정확히 한 번만 실행되어야 한다. 같은 키가 다른 요청에 재사용되는 경우에는 이전 응답을 잘못
반환하지 않아야 한다.

## 결정

- 예약 생성과 확정 API는 `Idempotency-Key` 헤더를 필수로 받는다.
- 키의 유효 범위는 회원과 명령 단위로 나눈다. 생성은 `reservation:create`, 확정은
  `reservation:confirm:{reservationId}` 범위를 사용한다.
- 요청 본문에서 정규화한 문자열의 SHA-256 해시를 저장한다. 결제 토큰 원문은 저장하지 않는다.
- PostgreSQL의 `(member_id, request_scope, idempotency_key)` 유니크 제약과 조건부
  `INSERT ... ON CONFLICT`로 키 획득을 원자적으로 처리한다.
- 키 획득, 비즈니스 상태 변경과 성공 응답 JSONB 저장은 같은 DB 트랜잭션에 포함한다.
- 같은 키와 같은 지문은 저장된 성공 응답을 재생하고, 지문이 다르면
  `409 IDEMPOTENCY_KEY_REUSED`를 반환한다.
- 보관 기간은 24시간이다. 만료된 행은 같은 키가 다시 들어오면 조건부 갱신해 재사용한다.
- 처리 실패 시 트랜잭션 전체를 롤백한다. 실패 응답은 저장하지 않아 같은 키로 안전하게
  재시도할 수 있다.

## 결과와 남은 위험

동시에 같은 생성 요청이 들어와도 하나의 요청만 예약과 재고를 변경하고 나머지는 커밋된 응답을
재생한다. 동일한 확정 요청도 모의 결제 승인을 한 번만 호출한다. 이 동작은 PostgreSQL을 사용한
통합 테스트로 검증한다.

현재는 성공 응답만 저장하므로 반복되는 영구 실패 요청의 부하는 줄이지 못한다. 응답 JSONB가
누적되므로 만료 행 정리 작업과 저장 용량 모니터링도 필요하다. 실제 PG 연동 시에는 DB 트랜잭션과
외부 승인 사이의 원자성이 보장되지 않으므로 같은 멱등키를 PG에도 전달하고 결제 시도 저장,
Transactional Outbox, 재처리와 대사 절차를 함께 도입해야 한다.
