# ADR-0010: 관리자 예약·재고 QueryDSL 조회 모델

- 상태: 승인
- 결정일: 2026-09-12

## 맥락

운영자는 예약 상태와 회원, 이벤트, 생성 기간을 조합해 검색하고 잔여 재고와 품절 항목을 빠르게
찾아야 한다. 엔티티를 그대로 반환하면 지연 로딩에 따른 N+1, 과도한 열 조회, API와 영속 모델의
결합이 생긴다. 컬렉션 fetch join과 offset 페이지네이션을 함께 쓰면 결과 행이 증폭되어 페이지가
왜곡될 수 있다.

## 결정

- 관리자 읽기 모델을 `admin` 모듈로 분리하고 QueryDSL DTO Projection을 사용한다.
- 예약 목록은 예약 항목 수와 총수량을 DB에서 그룹 집계한다. 본문 쿼리 1회와 전체 건수 쿼리
  1회로 고정하고 엔티티 그래프를 로딩하지 않는다.
- 재고 목록은 이벤트·회차를 명시적으로 조인해 총수량, 잔여 수량과 판매(선점) 수량을 한 행으로
  반환한다. 이 목록도 본문과 전체 건수 총 2회로 고정한다.
- 예약 정렬은 `created_at DESC, id DESC`로 고정한다. 같은 생성 시각에도 ID가 결정적
  tie-breaker가 된다.
- 재고 정렬은 `event_session.starts_at, event.id, event_session.id, inventory.id` 오름차순으로
  고정해 운영 화면의 순서가 페이지 호출마다 바뀌지 않게 한다.
- 상태별 예약 수와 확정 매출은 한 번의 `GROUP BY status` 쿼리로 계산하며, 데이터가 없는 상태도
  0으로 반환한다.
- 1만 건 PostgreSQL 데이터에서 상태·생성 시각 복합 인덱스가 사용되는지 통합 테스트로 확인한다.

## 대안

- Spring Data 메서드 쿼리는 선택 조건 조합과 집계 Projection이 늘어날수록 메서드가 분기별로
  증가해 제외했다.
- 엔티티 fetch join 뒤 애플리케이션 집계는 전송량과 영속성 컨텍스트 메모리를 불필요하게
  늘리므로 제외했다.
- 처음부터 Native SQL로 고정하면 타입 안전성과 조건 조합 가독성을 잃는다. 실행 계획으로
  QueryDSL 생성 SQL의 병목이 확인될 때만 해당 조회에 한정해 검토한다.

## 결과와 남은 위험

관리자 목록의 SQL 수와 정렬 계약을 자동 테스트로 고정했고, 운영 집계를 별도 읽기 모델로
노출했다. 현재 페이지네이션은 offset 방식이므로 깊은 페이지에서 스캔 비용이 증가한다. 다음
작업에서 `(created_at, id)` 커서를 도입하고 offset 크기에 따른 p50/p95/p99를 비교한다.

확정 매출은 현재 환불·부분 취소를 별도 원장으로 보관하지 않는 MVP 수치다. 실제 결제 연동 전에는
결제/환불 원장을 기준으로 매출 정의를 다시 고정해야 한다.
