# ADR-0016: 런타임 OpenAPI 계약과 대상별 문서 그룹

- 상태: Accepted
- 결정일: 2026-09-13

## 배경

API 수가 늘면서 README에 경로를 수동으로 나열하는 방식만으로는 요청 스키마, 검증 조건과 인증
요구 사항이 실제 컨트롤러와 달라질 수 있다. 포트폴리오 시연에서는 공개 조회, 회원 예약, 관리자
운영 API의 경계를 빠르게 설명할 수 있어야 하고, 계약 변경도 자동 테스트에서 감지해야 한다.

## 결정

- Spring Boot 3 계열과 호환되는 springdoc 2.x를 사용해 실행 중인 컨트롤러와 Bean Validation
  메타데이터에서 OpenAPI 3 계약을 생성한다.
- 전체 계약과 별도로 `public`, `member`, `admin` 그룹을 제공한다.
- JWT 인증은 재사용 가능한 `bearerAuth` 보안 스키마로 정의한다.
- 공개 로그인·이벤트 조회에는 보안 요구를 붙이지 않고, 회원·예약·관리자 API에만 명시한다.
- 400·401·403·404·409·422·429 오류를 재사용 가능한 응답 컴포넌트로 정의하고 실제 발생 가능한
  엔드포인트에 연결한다. 각 컴포넌트는 안정적인 오류 코드, 메시지, traceId와 details 예시를 제공한다.
- 예약 생성의 429 계약에는 클라이언트 재시도 시점을 위한 `Retry-After` 헤더를 포함한다.
- 계약 통합 테스트가 그룹별 핵심 경로, 공개 API의 비인증 상태, 보호 API의 JWT 요구와 Swagger UI
  진입 경로뿐 아니라 핵심 예외 응답의 상태 코드·컴포넌트 연결·예시를 검증한다.
- 로컬과 포트폴리오 시연에서는 문서를 기본 활성화한다. 운영에서는
  `SPRINGDOC_API_DOCS_ENABLED=false`, `SPRINGDOC_SWAGGER_UI_ENABLED=false`로 비활성화하거나
  내부망과 별도 인증 경계 뒤에 둔다.

## 대안

- 정적 YAML을 직접 관리하면 리뷰 시 계약이 명시적이지만 컨트롤러와 이중 관리되어 표류 가능성이
  커진다.
- 모든 API를 한 문서에만 제공하면 설정은 단순하지만 사용자 역할별 시연과 권한 검토가 어렵다.
- Swagger UI를 운영에 항상 공개하면 디버깅은 편하지만 공격 표면과 내부 계약 노출이 늘어난다.

## 결과

요청 모델과 검증 규칙의 변경이 실행 중인 계약에 즉시 반영되고, 역할별 API 경계를 독립된 JSON으로
검토할 수 있다. Swagger UI에서 정상 응답과 함께 검증 실패, 인증·인가, 리소스 없음, 재고·상태·멱등성
충돌, 결제 거절과 요청 제한의 실제 본문 형태를 확인할 수 있다. 계약 테스트는 핵심 경로, 인증
메타데이터와 예외 연결이 의도치 않게 빠지는 회귀를 막는다. 새로운 도메인 오류를 추가할 때는 예외
핸들러의 상태·코드와 OpenAPI 컴포넌트 예시를 함께 갱신한다.
