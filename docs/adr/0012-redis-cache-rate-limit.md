# ADR-0012: Redis Cache-Aside와 예약 속도 제한

- 상태: 승인
- 결정일: 2026-09-12

## 맥락

공개 이벤트 상세는 읽기 비중이 높고 이벤트 판매가 시작되면 같은 내용을 반복 조회한다. 반대로
판매 오픈 시점의 예약 생성은 짧은 시간에 한 회원이나 자동화된 클라이언트의 요청이 몰려 DB
커넥션과 재고 경합을 키울 수 있다. Redis를 사용하더라도 장애가 예약·조회 원본 기능의 전체
장애로 번져서는 안 된다.

## 결정 — 공개 상세 캐시

- `GET /api/events/{eventId}`에 Cache-Aside를 적용한다.
- 키는 `cache:event-detail:v1:{eventId}`, 기본 TTL은 5분이다. 버전 접두어로 응답 스키마 변경 시
  새 namespace로 전환할 수 있다.
- hit이면 DB를 조회하지 않고, miss이면 기존 QueryDSL 상세 조회 후 JSON을 Redis에 저장한다.
- 이벤트 제목·상태, 아티스트, 회차와 재고 변경은 관련 event ID를 수집해 DB 커밋 이후 키를
  삭제한다. 롤백된 변경이 정상 캐시를 불필요하게 제거하지 않도록 `afterCommit`에 묶는다.
- Redis 연결·직렬화 실패는 캐시 miss로 취급해 DB 원본을 반환한다. 캐시 저장·삭제 실패도 원본
  트랜잭션과 응답을 실패시키지 않는다.

## 결정 — 예약 생성 속도 제한

- `POST /api/reservations`에 회원별 fixed-window 제한을 적용한다. 기본값은 1분 20회다.
- Redis Lua에서 `INCR`, 최초 요청의 `PEXPIRE`, 남은 TTL 조회를 원자적으로 실행한다.
- 초과 요청은 비즈니스 트랜잭션 진입 전에 429와 `Retry-After`를 반환하므로 재고·예약·멱등키가
  변경되지 않는다.
- Redis 장애 시 예약은 fail-open한다. 가용성을 우선하되 경고 로그와 후속 메트릭으로 장애를
  감지한다.

## 대안

- Spring Cache 추상화는 단순 hit/miss에는 편하지만 DB 커밋 이후 세밀한 무효화와 Redis 장애
  정책을 코드에서 명확히 보여주기 위해 현재 범위에서는 직접 Cache-Aside를 선택했다.
- 로컬 메모리 제한은 다중 인스턴스에서 회원 요청 수를 합산할 수 없어 제외했다.
- DB 기반 요청 카운터는 판매 오픈 부하를 DB 쓰기로 되돌리므로 제외했다.
- token bucket은 경계 순간 burst를 더 부드럽게 제어하지만 구현·운영 복잡도가 증가한다. 현재
  fixed-window의 경계 특성을 측정한 뒤 필요할 때 전환한다.
- Redis 장애 시 fail-closed는 과다 요청을 확실히 막지만 정상 사용자 예약까지 전체 차단하므로
  현재 가용성 목표와 맞지 않는다.

## 검증

- 첫 상세 조회는 QueryDSL SQL 2회, 두 번째 동일 조회는 SQL 0회다.
- 저장된 키의 TTL이 1~300초 범위인지 확인한다.
- 이벤트 수정 트랜잭션 커밋 직후 키가 삭제되고 다음 조회가 변경된 제목을 DB에서 다시 읽는다.
- Redis 연결 예외 시 상세 서비스가 DB 원본을 반환하고 캐시 쓰기·삭제 예외도 전파하지 않는다.
- 같은 회원의 20개 예약은 성공하고 21번째는 429이며, 재고 차감과 예약 저장은 정확히 20건이다.

## 결과와 남은 위험

읽기 hit는 DB SQL을 제거하고, 예약 초과 요청은 재고 트랜잭션 전에 차단된다. 캐시 장애가 원본
기능을 중단시키지 않는 대신 장애 중 DB 부하가 급증할 수 있고 속도 제한도 약화된다. Redis 장애,
cache hit/miss, rate-limit reject 메트릭과 경보를 다음 운영 관측 작업에서 추가한다.

fixed-window는 구간 경계 앞뒤로 최대 2배에 가까운 요청이 통과할 수 있다. 실제 판매 오픈 부하
시험에서 문제가 확인되면 sliding-window 또는 token bucket을 비교한다. 캐시 stampede도 현재
TTL이 동시에 만료되는 인기 이벤트에서 발생할 수 있어 TTL jitter나 짧은 분산 잠금을 후속으로
검토한다.
