# ADR-0018: 결제 시도 원장과 결과 불명 대사

## 상태

채택

## 맥락

PG 승인 요청과 예약 확정 DB 커밋은 하나의 원자적 트랜잭션으로 묶을 수 없다. PG가 승인을 완료한 뒤 응답이 유실되거나 애플리케이션이 종료되면 사용자는 실패처럼 보이는 응답을 받지만 실제 결제는 승인됐을 수 있다. 이때 요청을 그대로 반복하면 중복 승인 위험이 있고, 예약을 즉시 실패 처리하면 결제와 예약 상태가 어긋난다.

## 결정

- 승인 호출 전에 예약 ID, 금액, PG 멱등키, 결제 토큰의 SHA-256 fingerprint를 `payment_attempts`에 저장한다. 결제 토큰 원문은 저장하지 않는다.
- PG 멱등키는 예약 ID와 확정 요청의 `Idempotency-Key` 해시로 만들며 유일 제약으로 보호한다.
- 상태는 `REQUESTED`, `APPROVED`, `DECLINED`, `UNKNOWN`으로 구분한다.
- 승인·거절·타임아웃 결과는 `REQUIRES_NEW` 트랜잭션으로 결제 시도 원장에 먼저 확정한다. 예약 트랜잭션이 이후 실패해도 PG 결과를 잃지 않는다.
- 타임아웃은 `409 PAYMENT_RESULT_UNKNOWN`으로 반환하며 같은 PG 멱등키로 승인 API를 다시 호출하지 않는다.
- 관리자는 QueryDSL 기반 `GET /api/admin/payment-attempts/unknown`에서 결과 불명 시도를 조회하고, `POST /api/admin/payment-attempts/{id}/reconcile`로 PG 조회 결과를 반영한다.
- 대사 결과가 승인이고 예약이 여전히 확정 가능하면 결제 시도 `APPROVED`, 예약 `CONFIRMED`, Outbox 이벤트와 감사 로그를 하나의 트랜잭션에서 저장한다.
- 대사 결과가 거절이면 결제 시도만 `DECLINED`로 수렴시킨다. 아직 PG 결과가 없으면 `UNKNOWN`을 유지한다.
- 대사 결과별 `fan.event.payment.reconciliation` 메트릭을 남긴다.

## 대안

- 타임아웃을 즉시 결제 실패로 처리하면 구현은 단순하지만 실제 승인과 예약 상태 불일치를 숨긴다.
- 모든 타임아웃 요청을 다시 승인하면 PG가 멱등성을 완전하게 제공하지 않을 때 중복 결제가 발생한다.
- 결제 토큰을 원문 저장하면 재처리는 쉬워지지만 민감정보 저장 범위와 유출 영향을 불필요하게 키운다.
- PG webhook만 기다리면 정상 수렴은 가능하지만 누락·지연 시 운영자가 상태를 조회하고 복구할 공식 경로가 없다.

## 결과

승인 응답 유실을 명시적인 운영 상태로 드러내고, 사용자 재시도가 추가 승인 호출을 만들지 않게 됐다. 결제 원장과 예약·Outbox·감사 로그가 복구 근거를 제공하며, 관리자 대사를 반복해도 예약 확정 이벤트는 한 번만 생성된다.

## 남은 위험

- 승인 확인 시점에 예약이 이미 만료·취소됐다면 자동 확정하지 않고 수동 보상 판단이 필요하다.
- 현재 모의 PG의 조회 결과는 프로세스 메모리에 있으므로 실제 연동에서는 PG 조회 API와 webhook 서명 검증이 필요하다.
- 외부 호출 동안 DB 트랜잭션을 점유하지 않도록 승인 오케스트레이션을 더 세분화할 수 있다.
- 환불 역시 별도 시도 원장과 결과 불명 상태를 적용해야 완전한 대칭 구조가 된다.
