# ADR-0020: 결과 불명 자동 대사 임대와 백오프

## 상태

채택

## 맥락

결제·환불 응답 유실은 원장과 관리자 단건 대사로 복구할 수 있지만, 운영자가 목록을 계속 확인해야 하면 복구 시간이 사람의 대응 속도에 종속된다. 여러 애플리케이션 인스턴스가 같은 `UNKNOWN` 건을 동시에 조회하면 PG 조회와 감사 기록이 중복될 수 있고, 외부 호출 동안 DB 잠금을 유지하면 느린 PG가 커넥션과 잠금 자원을 소모한다. 작업 도중 프로세스가 종료된 건도 영구히 고착되지 않아야 한다.

## 결정

- 결제·환불 원장에 대사 시도 횟수, 다음 실행 시각, 처리 임대 만료 시각과 최근 실행 시각을 저장한다.
- 짧은 새 트랜잭션에서 실행 시각이 도래했고 임대가 없거나 만료된 `UNKNOWN`을 `FOR UPDATE SKIP LOCKED`로 최대 20건 선점한다.
- 선점 트랜잭션을 커밋한 뒤 기존 관리자 대사 서비스를 호출한다. PG 조회 중에는 선점 행 잠금을 점유하지 않으며 결제·예약·Outbox·감사 로그의 최종 수렴 로직은 공유한다.
- 아직 결과가 없거나 조회가 실패하면 10초에서 시작해 최대 10분인 지수 백오프로 다음 실행을 예약한다. 해결된 건은 실행 시각과 임대를 제거한다.
- 프로세스가 중단되면 30초 임대가 만료된 뒤 다른 인스턴스가 다시 선점한다.
- 자동 실행 감사 주체는 `system:auto-reconciliation`으로 구분하고, 결제·환불별 처리 결과 counter와 backlog·최장 체류 시간 gauge를 공개한다.
- 최장 체류 시간이 5분을 넘는 상태가 5분 지속되면 Prometheus 경보를 발생시킨다. 수동 대사는 긴급 복구 경로로 유지한다.

## 구현 선택

애그리거트 상태 변경과 최종 수렴에는 JPA를 유지한다. 다중 인스턴스에서 선점과 임대 갱신을 하나의 원자 연산으로 수행하려면 PostgreSQL의 `SKIP LOCKED`와 `UPDATE ... RETURNING`이 필요하므로 이 좁은 배치 경계에만 Native SQL을 사용한다. 관리자 동적 목록은 기존 QueryDSL 읽기 모델을 그대로 사용한다.

## 대안

- 스케줄러가 목록을 읽고 건별로 처리하면 구현은 단순하지만 읽기와 임대 갱신 사이 경쟁으로 중복 선점할 수 있다.
- PG 조회가 끝날 때까지 행 잠금을 유지하면 중복은 막지만 외부 장애가 DB 트랜잭션과 커넥션 고갈로 전파된다.
- 고정 간격 재시도는 복구 예상이 단순하지만 장시간 PG 장애에서 불필요한 조회 부하가 계속된다.
- 메시지 브로커의 지연 큐는 확장성이 높지만 현재 모듈형 모놀리스의 운영 복잡도에 비해 과도하다.

## 결과

결제·환불 결과 불명 건이 사람의 개입 없이 기존 정합성 경계로 수렴한다. 복수 작업자는 같은 건을 한 번만 선점하고, 장애로 남은 임대는 자동 회수된다. 결과가 계속 없을 때 조회 부하는 상한이 있는 백오프로 억제되며, backlog와 최장 체류 지표로 복구 지연을 감지할 수 있다.

## 남은 위험

- 실제 PG의 조회 제한과 권장 polling 간격에 맞춰 배치 크기와 백오프를 조정해야 한다.
- 승인 확인 시 예약이 이미 만료된 보상 사건은 자동 확정하지 않으며 별도 보상 정책이 필요하다.
- webhook을 도입하더라도 누락 복구를 위해 조회 기반 대사는 보조 경로로 유지한다.
