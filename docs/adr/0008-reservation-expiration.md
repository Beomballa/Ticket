# ADR-0008: 예약 만료 선점과 재고 반환

- 상태: 승인
- 결정일: 2026-09-12

## 맥락

결제되지 않은 `PENDING` 예약은 선점 시간이 지나면 재고를 반환해야 한다. 애플리케이션이 여러
인스턴스로 실행되거나 스케줄 작업이 중복 실행되어도 같은 예약을 두 번 처리해서는 안 된다.
작업 도중 프로세스가 중단된 경우에는 다음 실행이 안전하게 이어받을 수 있어야 한다.

## 결정

- 1초 고정 지연 스케줄로 만료 작업을 실행하고 한 번에 최대 50건을 처리한다. 주기와 배치 크기는
  설정으로 변경할 수 있다.
- 다음 쿼리로 만료된 `PENDING` 예약 ID를 만료 시각·ID 순으로 선점한다.

```sql
SELECT id
FROM reservations
WHERE status = 'PENDING'
  AND expires_at <= :now
ORDER BY expires_at, id
FOR UPDATE SKIP LOCKED
LIMIT :batchSize
```

- 초기 스키마의 `idx_reservations_expiration (expires_at, id) WHERE status = 'PENDING'` 부분
  인덱스를 그대로 사용한다.
- 예약을 `EXPIRED`로 변경하고 모든 항목의 재고를 반환하는 작업을 하나의 트랜잭션에서 수행한다.
- 재고 반환은 `available_quantity + quantity <= total_quantity` 조건부 UPDATE를 사용하고
  `version`도 증가시킨다.
- 여러 재고는 ID 순으로 반환해 서로 다른 배치 사이의 교착 가능성을 줄인다.
- 트랜잭션이 커밋되기 전에 작업이 중단되면 예약 상태와 재고 반환이 모두 롤백된다. 행 잠금도
  해제되므로 다음 실행이 같은 예약을 다시 선점한다.

## 대안

- 상태를 먼저 `PROCESSING`으로 바꾸는 별도 선점 단계는 장시간 작업에는 유리하지만, 프로세스
  중단 시 임대 만료와 복구 상태가 추가로 필요하다. 현재 만료 처리는 짧은 DB 트랜잭션이므로
  행 잠금 방식을 선택했다.
- 전체 대상 조회 후 JPA 낙관적 락만 사용하는 방식은 여러 인스턴스가 같은 예약을 읽고 충돌과
  롤백을 반복할 수 있어 제외했다.
- 분산 락은 DB 행이 실제 정합성 원본인 상황에서 별도 장애 지점과 잠금 유실 문제를 추가하므로
  사용하지 않는다.

## 결과와 남은 위험

중복 실행, 동시 실행과 강제 롤백 후 재실행 테스트에서 예약 상태와 재고가 정확히 한 번만
변경되는 것을 검증한다. 배치 하나가 실패하면 해당 배치 전체가 롤백되며 다음 실행에서 재시도된다.

대량 적체 시 한 번에 한 배치만 처리하므로 해소 속도가 제한될 수 있다. 운영 단계에서는 만료
대상 수, 처리 건수, 실패 횟수와 지연 시간을 메트릭으로 노출하고 필요하면 실행당 최대 배치 수를
추가한다. 실제 결제 승인과 만료가 경합하는 경계는 PG 멱등키와 결제 시도 상태 머신을 포함해
별도 보강해야 한다.
