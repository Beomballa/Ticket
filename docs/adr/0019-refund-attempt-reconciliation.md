# ADR-0019: 환불 시도 원장과 결과 불명 대사

## 상태

채택

## 맥락

PG 환불과 예약 취소 DB 커밋은 하나의 원자적 트랜잭션으로 묶을 수 없다. PG가 환불을 완료한 뒤 응답이 유실되면 같은 취소를 반복할 때 중복 환불할 수 있다. 반대로 결과 불명 상태에서 예약을 먼저 취소하고 재고를 반환하면 실제 환불 거절 고객의 재고가 다시 판매되는 상태 불일치가 발생한다.

## 결정

- `CONFIRMED` 예약 취소는 승인된 `payment_attempts`를 참조하는 `refund_attempts` 원장을 먼저 생성한다.
- 환불 시도는 예약별 한 건이며 `reservation-refund-{reservationId}` PG 멱등키를 사용한다. 예약 ID와 PG 멱등키를 각각 유일 제약으로 보호한다.
- 상태는 `REQUESTED`, `SUCCEEDED`, `DECLINED`, `UNKNOWN`으로 구분한다.
- 환불 성공·거절·타임아웃은 `REQUIRES_NEW` 트랜잭션으로 원장에 먼저 확정한다. 이후 예약 취소 트랜잭션이 실패해도 재시도는 성공 원장을 재사용하고 PG를 다시 호출하지 않는다.
- 결과 불명은 `409 REFUND_RESULT_UNKNOWN`과 `refundAttemptId`를 반환한다. 이 동안 예약은 `CONFIRMED`, 재고는 선점 상태로 유지한다.
- 관리자는 QueryDSL 기반 `GET /api/admin/refund-attempts/unknown`으로 대상을 조회하고 `POST /api/admin/refund-attempts/{id}/reconcile`로 PG 결과를 반영한다.
- 성공 대사는 환불 시도 `SUCCEEDED`, 예약 `CANCELLED`, 재고 반환, Outbox와 감사 로그를 하나의 트랜잭션으로 저장한다.
- 거절 대사는 환불 시도만 `DECLINED`로 수렴시키며 예약과 재고는 변경하지 않는다. PG 결과가 아직 없으면 `UNKNOWN`을 유지한다.
- 대사 결과별 `fan.event.refund.reconciliation` 메트릭을 남긴다.

## 대안

- 환불 호출 전에 예약을 취소하면 응답은 빠르지만 환불 거절 시 이미 반환된 재고와 예약 상태를 되돌려야 한다.
- 타임아웃마다 환불을 다시 호출하면 PG 멱등성 계약이 약하거나 키가 달라질 때 중복 환불 위험이 있다.
- 환불을 Outbox 비동기 명령으로만 처리하면 요청 지연은 줄지만 고객에게 취소 완료와 환불 완료의 구분을 새로 노출해야 한다.

## 결과

정상 취소와 운영 대사가 같은 예약 취소 완료 로직을 사용한다. 환불 결과가 확인되기 전에는 재고를 재판매하지 않으며, 환불 성공 뒤 로컬 커밋이 실패해도 다음 요청이 성공 원장을 재사용해 예약·재고·Outbox를 한 번만 수렴시킬 수 있다.

## 남은 위험

- 실제 PG는 부분 환불, 환불 가능 기간, 원거래 취소와 환불 상태 어휘가 다르므로 어댑터 계약을 PG 사양에 맞춰 확장해야 한다.
- 모의 PG의 환불 조회 결과는 프로세스 메모리에 있으므로 실제 연동에서는 조회 API와 webhook 서명 검증이 필요하다.
- 오래된 `UNKNOWN` 자동 대사 스케줄러와 체류 시간 경보는 후속 운영 확장으로 남는다.
