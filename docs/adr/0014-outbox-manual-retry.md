# ADR-0014: 최대 시도 Outbox 이벤트의 수동 재처리

## 상태

채택

## 맥락

Outbox 퍼블리셔는 실패 이벤트를 최대 5회까지 지수 백오프로 다시 처리한다. 최대 횟수에 도달한 행은 자동 선점 조건 `attempts < maxAttempts`에서 제외되므로 데이터는 보존되지만 운영자가 원인 해소 후 다시 투입할 공식 경로가 없었다. DB 직접 수정은 인가, 동시 요청 제어와 감사 기록을 우회한다.

## 결정

- 관리자만 상태·이벤트 유형·aggregate ID·최소 시도 횟수·생성 기간으로 Outbox 이벤트를 조회한다.
- 목록은 QueryDSL DTO projection으로 payload를 제외하고 `created_at DESC, id DESC` 순서를 고정한다.
- 별도 `exhausted` 목록은 현재 설정의 `maxAttempts`를 사용해 수동 재처리 가능한 이벤트만 반환한다.
- 재처리는 `FAILED AND attempts >= maxAttempts` 조건부 UPDATE 한 번으로 `PENDING`, `attempts=0`, `available_at=now`로 되돌린다.
- 조건부 UPDATE 영향 행이 0이면 `409 OUTBOX_RETRY_REJECTED`로 응답한다. 이 조건이 같은 이벤트에 대한 동시 관리자 요청 중 하나만 성공하게 만든다.
- 성공한 재처리는 같은 트랜잭션에서 `audit_logs`에 이전 시도 횟수와 관리자 subject를 기록하고, accepted/rejected 메트릭과 구조화 로그를 남긴다.

## 대안

- DB runbook SQL만 제공하면 구현은 간단하지만 인가와 감사, 동시성 보장을 잃는다.
- 실패 이벤트를 복제하면 원본 보존은 쉽지만 새 UUID가 소비자 멱등 키를 바꾸어 같은 부작용이 다시 실행될 수 있다.
- 시도 횟수를 1만 줄이면 직전 백오프 상태와 운영자의 명시적 재시작 의도가 불명확하다. 새 수동 처리 주기로 reset하는 편이 관측하기 쉽다.

## 결과

운영자는 격리된 이벤트를 API와 콘솔에서 찾고 원인을 해소한 뒤 안전하게 재투입할 수 있다. 자동 퍼블리셔는 다음 poll에서 기존 이벤트 ID를 전달하므로 소비자 멱등성이 유지된다. 시도 횟수가 reset되므로 전체 생애 누적 시도 수는 감사 로그와 metric에서 추적해야 한다.

## 남은 위험

- 재처리 전에 외부 시스템 장애가 해소됐는지는 운영자가 확인해야 한다.
- payload는 목록에서 숨겼으며, 별도 payload 확인 기능을 만들 경우 개인정보 마스킹과 접근 감사를 추가해야 한다.
- 다건 재처리, 승인 workflow와 보존·삭제 정책은 현재 범위 밖이다.
