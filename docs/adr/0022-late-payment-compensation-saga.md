# ADR-0022: 예약 만료 후 늦은 승인 보상 환불 Saga

## 상태

채택

## 맥락

결제 승인 응답이 유실된 사이 예약이 만료되면 재고는 이미 반환된다. 이후 PG 조회나 웹훅에서 승인이 확인돼도 예약을 다시 확정하면 다른 구매자에게 판매된 재고를 중복 배정할 수 있고, 승인만 기록하면 고객 과금과 예약 상태가 불일치한다. 외부 환불은 DB 트랜잭션과 원자적으로 묶을 수 없으므로 중단·응답 유실·중복 작업을 전제로 수렴해야 한다.

## 결정

- 만료 예약의 승인이 확인되면 결제 원장을 `APPROVED`로 확정하되 예약은 `EXPIRED`, 반환된 재고는 그대로 유지한다.
- 같은 트랜잭션에서 기존 `refund_attempts`에 목적 `LATE_PAYMENT_COMPENSATION`인 보상 환불을 생성한다. 키는 예약별 `late-payment-compensation-{reservationId}`로 고정한다.
- 일반 예약 취소 환불과 보상 환불을 `purpose`로 구분한다. 보상 성공 시 예약 취소·재고 반환·취소 Outbox를 실행하지 않는다.
- 짧은 트랜잭션이 `REQUESTED` 보상을 만료 가능한 임대로 선점한 뒤 외부 환불을 호출한다. 성공·거절은 원장에 확정하고 응답 유실은 `UNKNOWN`으로 전환해 기존 조회 대사와 지수 백오프를 사용한다.
- 관리자 목록은 QueryDSL projection으로 제공하고, 결과 불명은 조회 대사하며 거절·대기 건은 같은 PG 멱등키로 다시 요청할 수 있다.

## 구현 선택

새 보상 전용 환불 원장을 만들지 않고 기존 환불 원장에 목적을 추가했다. 환불 멱등키, 상태 머신, 조회 대사와 운영 지표를 공유하면서 예약 후처리만 목적별로 분리할 수 있기 때문이다. JPA는 결제 승인·보상 생성과 상태 전이에, QueryDSL은 운영 조회에 사용한다. 다중 작업자 선점에만 `UPDATE ... RETURNING` Native SQL을 유지한다.

## 결과

늦은 승인은 예약과 재고를 되돌리지 않고 자동 환불로 수렴한다. 웹훅 중복과 복수 작업자가 있어도 보상 원장은 예약당 한 건이고 PG 환불은 고정 멱등키를 사용한다. 응답 유실은 기존 환불 조회 경로로 복구되며 backlog와 최장 체류 시간으로 운영자가 감지한다.

## 남은 위험

- 실제 PG가 거절된 동일 멱등키 재요청을 어떻게 처리하는지 sandbox 계약을 확인해야 한다.
- 부분 승인·부분 환불과 수수료 정책은 현재 전액 보상 모델 밖이다.
- 장기간 해결되지 않은 보상의 고객 알림과 상담 티켓 연동은 후속 범위다.
