# ADR-0011: 예약 `(created_at, id)` 커서 페이지네이션

- 상태: 승인
- 결정일: 2026-09-12

## 맥락

offset 페이지네이션은 사용법과 전체 페이지 표현이 단순하지만, 깊은 페이지에 도달할수록 앞선
행을 읽고 버려야 한다. 관리자 예약 목록은 지속적으로 데이터가 추가되므로 페이지 이동 중 신규
예약이 들어오면 offset 경계가 밀려 중복 또는 누락도 발생할 수 있다.

## 결정

- 깊은 순차 탐색용 `GET /api/admin/reservations/cursor`를 별도로 제공한다. 기존 offset API는
  임의 페이지 이동과 전체 건수가 필요한 관리 기능을 위해 유지한다.
- 정렬과 커서 키는 `created_at DESC, id DESC`로 일치시킨다. ID가 같은 생성 시각의
  tie-breaker이므로 순서가 결정적이다.
- 커서는 생성 시각과 예약 ID를 URL-safe Base64로 인코딩한다. 클라이언트는 내부 구조에
  의존하지 않고 응답 문자열을 그대로 재전송한다.
- 다음 페이지는 PostgreSQL 행 값 비교 `(created_at, id) < (?, ?)`로 조회한다. QueryDSL의
  `booleanTemplate` 사용은 이 PostgreSQL 전용 seek 조건 한 곳으로 제한한다.
- `size + 1`건을 조회해 다음 페이지 존재 여부를 판단한다. count 쿼리를 제거해 페이지당 SQL을
  1회로 고정한다.
- 기존 `idx_reservations_member_created (member_id, created_at DESC, id DESC)`가 회원 조건
  커서 seek를 지원하므로 동일 목적의 인덱스를 추가하지 않는다. 상태 중심 조회는 V3의
  `idx_reservations_status_created`를 사용한다.

## 실패한 접근과 교정

처음에는 동등한 논리식인 `created_at < ? OR (created_at = ? AND id < ?)`를 사용했다. 5만 건
49,001번째 경계에서 PostgreSQL이 이를 효율적인 복합 인덱스 시작점으로 사용하지 못해 커서
p50 3.276ms, p95 3.423ms, p99 3.801ms로 offset과 사실상 같았다.

행 값 비교로 바꾸자 실행 계획의 `Index Cond`에 `ROW(created_at, id) < ROW(...)`가 포함되고,
같은 위치에서 p50 0.213ms, p95 0.295ms, p99 0.376ms로 감소했다.

## 대안

- offset만 유지하면 전체 페이지 이동은 쉽지만 깊이에 비례한 비용과 변경 중 페이지 경계 문제를
  해결하지 못한다.
- 커서에 전체 필터를 직렬화하거나 서버 저장형 토큰을 쓰는 방식은 현재 계약에 불필요한 상태와
  운영 비용을 만든다.
- 커서 전용 중복 인덱스는 쓰기 비용과 저장 공간만 늘리므로 실제 실행 계획이 기존 인덱스를
  사용함을 확인하고 제외했다.

## 결과와 남은 위험

커서 API는 깊이에 관계없이 경계 이후 21건만 찾고, 두 연속 페이지에서 중복 없이 안정적인 순서를
유지한다. 잘못된 커서와 1~100 범위를 벗어난 페이지 크기는 400으로 거부한다.

Base64는 위변조 방지가 아니라 불투명 표현만 제공한다. 커서 조건은 조회 권한을 넓히지 않지만,
장기 공개 API가 되면 버전 필드와 HMAC 서명을 검토한다. 또한 커서는 요청 사이의 스냅샷을
고정하지 않으므로 기존 행의 생성 시각을 수정하지 않는 불변식을 유지해야 한다.
