# ADR-0015: 사용자 내 예약 QueryDSL 읽기 모델

## 상태

채택

## 맥락

예약 생성·확정·취소는 구현됐지만 사용자가 자신의 예약 이력을 다시 확인할 공식 조회 경로가 없었다. 쓰기 애그리거트를 API로 직접 반환하거나 예약 항목을 fetch join한 채 페이지네이션하면 영속 모델이 외부 계약에 결합되고, 컬렉션 행 증폭으로 페이지와 count가 왜곡될 수 있다. 요청 파라미터로 회원 ID를 받으면 다른 회원 데이터 조회를 시도할 여지도 생긴다.

## 결정

- 목록과 상세의 회원 범위는 요청값이 아니라 검증된 JWT subject로만 정한다.
- 목록은 상태·생성 시작·종료 시각을 동적으로 조합하는 QueryDSL DTO Projection을 사용한다.
- 목록 본문은 항목 수·총수량·공연 수를 DB에서 집계하고, 본문 1회와 count 1회로 SQL 수를 고정한다.
- 정렬은 `created_at DESC, id DESC`로 고정하고 기존 `idx_reservations_member_created` 인덱스를 재사용한다.
- 하나의 예약이 여러 공연 재고를 담을 수 있는 현재 모델을 유지하므로 목록에는 공연 수와 대표 공연명 하나를 제공하고, 전체 공연·회차·재고 정보는 상세에서 반환한다.
- 상세는 소유권 조건을 포함한 헤더 쿼리와 항목 Projection 쿼리, 총 2회로 조립한다. 존재하지 않는 예약과 타인 예약은 모두 동일한 404 응답으로 처리해 존재 여부를 노출하지 않는다.
- 페이지 크기는 전역 Spring Data 설정으로 최대 100까지 제한한다.

## 대안

- `Reservation` 엔티티와 지연 로딩 컬렉션을 직접 직렬화하는 방식은 N+1과 순환 참조, API 계약 결합 때문에 제외했다.
- 컬렉션 fetch join 한 번으로 상세와 목록을 모두 처리하는 방식은 페이지 행 증폭과 메모리 중복 제거 비용 때문에 제외했다.
- 사용자 목록에도 즉시 keyset pagination을 적용하는 방안은 기존 회원·생성 시각 인덱스로 확장 가능하지만, 개인별 이력이 제한적인 MVP에서는 offset 계약을 먼저 제공하고 실제 깊이를 측정한 뒤 도입하기로 했다.

## 결과와 남은 위험

사용자는 상태·기간별로 자신의 예약만 조회하고 공연·회차·가격 스냅샷을 상세에서 확인할 수 있다. 목록과 상세의 SQL 수, 회원 격리, 정렬과 오류 계약은 통합 테스트로 고정한다.

현재 대표 공연명은 여러 공연이 포함된 예약의 모든 내용을 표현하지 않으므로 UI가 공연 수를 함께 표시한다. 예약 생성 단계에서 동일 이벤트만 허용할지는 상품 정책이 확정될 때 별도 도메인 규칙으로 결정한다. 개인 예약이 매우 많아지면 `(member_id, created_at, id)` 커서 페이지네이션으로 전환한다.
