# ADR-0025: 결제 확정의 순차 트랜잭션 경계

- 상태: 승인
- 결정일: 2026-09-15

## 맥락

예약 확정의 단일 트랜잭션이 먼저 DB 연결을 점유한 상태에서 결제 시도 원장을
`REQUIRES_NEW`로 기록했다. 동시 요청이 Hikari 최대 연결 수에 도달하면 각 요청이 외부
트랜잭션의 연결을 놓지 않은 채 두 번째 연결을 기다려, active 10·idle 0·pending 증가와
약 30초의 연결 획득 타임아웃이 발생했다.

결제 시도 원장은 PG 호출 전에 커밋되어야 하고 승인·거절·결과 불명도 예약 트랜잭션의
롤백과 무관하게 남아야 한다. 따라서 `REQUIRES_NEW`를 단순 제거하거나 풀 크기만 늘리는
방법은 선택하지 않는다.

## 결정

- 예약 소유권·만료·금액 검증은 짧은 읽기 트랜잭션에서 수행하고 스냅샷만 반환한다.
- 결제 시도 `REQUESTED`는 독립 트랜잭션으로 먼저 커밋한다.
- PG 승인 호출은 Spring DB 트랜잭션이 없는 상태에서 실행한다.
- `APPROVED`, `DECLINED`, `UNKNOWN` 원장 변경은 각각 독립 트랜잭션으로 커밋한다.
- 승인 후 예약 `CONFIRMED`, 성공 멱등 응답과 Outbox는 마지막 단일 트랜잭션에서 함께 커밋한다.
- 확정 시작 시각을 상태 전이 판단에 전달해 PG 응답 시간 때문에 선점 유효성 판단이 달라지지 않게 한다.
- Hikari active·pending·timeout을 대시보드와 경보에 추가하고, k6 스크립트는 부하 구간의 timeout 증가를 실패로 판정한다.

## 결과

각 단계는 동시에 최대 한 개의 DB 연결만 점유하며 PG 응답을 기다리는 동안에는 연결을
점유하지 않는다. 결제 승인 원장이 먼저 커밋되므로 마지막 예약 커밋이 실패해도 같은 PG
멱등키와 원장 상태로 재시도하거나 대사할 수 있다. 승인·거절·타임아웃·순차 멱등 재생과
늦은 승인 보상 흐름은 기존 회귀 테스트를 유지한다.

## 남은 고려사항

서로 다른 애플리케이션 인스턴스에서 같은 미완료 확정 요청이 완전히 동시에 시작되면 PG
멱등키와 결제 시도 유니크 키가 최종 중복 승인을 막는다. 사용자 경험을 위해 진행 중 응답을
대기 후 재생하는 기능이 필요하면 멱등 요청에 처리 임대와 소유 토큰을 추가하는 별도 작업으로 다룬다.
